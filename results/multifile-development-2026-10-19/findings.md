Exploratory CPU development used the 90 already-observed first-repetition Express/Zod searches. Exact compact baseline replay passed all90 cases. Selectors never received labels, query IDs, kinds, or evidence ranks. Gold was used only after selection. These experiments provide no fresh-holdout, retrieval-latency, token-billing or coding-correctness evidence.

Marginal lexical coverage, overlap penalties and path diversity did not yield a consistent improvement. All tested settings and regressions are retained in diversity-summary.json. Zod multi-file completion stayed0/4 across all these variants. Strong lexical prefixes improved Express hybrid while hurting Zod hybrid; broad pseudo-module filtering improved Express hybrid alone and risks suppressing meaningful initializers.

Literal clause retrieval changes the candidate pool. The algorithm splits only on comma/and/while/then, retains2–4 literal fragments with>=3 content terms, preserves the first3 distinct dense symbols, interleaves the first3 distinct-symbol lexical hits per clause, then appends remaining dense symbols, capped50. It retains the existing dependency expansion and exact8/12000-character/4096-token context caps. A full-query lexical control separates clause effects from merely adding lexical search. Both Python BM25 and actual persistent SQLite FTS5 were evaluated; all settings, losses and changed evidence-group ranks are retained.

Using the persistent FTS5 implementation with dense base ranks, Express remains10/12 complete and2/4 multi-file, while Zod improves8->9/12 complete and0->1/4 multi-file. The gain is metadata attachment/registry. The full-query lexical control does not reproduce it. Applying the same policy over hybrid base ranks loses one Express complete/multi-file case and brings no Zod gain; BM25 base ranks regress. First1 preservation regresses substantially. Thus only an explicit dense-based experimental mode is justified for independent validation; dense and hybrid defaults must remain unchanged.

The production MultifileRetriever helper reproduced the prototype's output IDs, group ranks, budgets and token counts in all90 cases. Returned priorities are1/(60+merged rank), not cosine confidence. The in-memory and persistent lexical probes are separate controls, not repetitions of an independent benchmark.

Scripts can be run with the main project .venv, PYTHONPATH set to the implementation checkout's src, TIKTOKEN_CACHE_DIR set to the existing verified tokenizer cache, --project-root pointing to the main checkout containing the historical results and corpora, and --output pointing to an ignored output file. Persistent probe databases remain beside the executing scripts; run copies in an ignored directory if reproducing locally. Summary receipts contain no source bodies. The binding records hashes after development and makes no prospective-freeze claim for these exploratory variants.
