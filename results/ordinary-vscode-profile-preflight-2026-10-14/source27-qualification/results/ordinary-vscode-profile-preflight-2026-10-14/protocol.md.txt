# Ordinary installed VS Code profile acceptance, prospective protocol

This check is authored before any ordinary-profile editor launch. It uses the existing pinned VS Code 1.141.0 / commit `2a59476c9bfcb90b3ddc372c36762471b7dfad1c` host from `extensions/vscode/scripts/host-config.cjs`. Its executable SHA-256 must remain `e9760eca0a62d96ff2bb334ef5c8d3b677a6275a2dd0cf5a63c356b7a19435a2`. There is no host download fallback, package installation, dependency installation, compilation, version change, publishing, embedding, indexing, search-engine execution, or model inference in preparation.

The helper is `scripts/ordinary_vscode_profile.cjs`; its normally installed sidecar lives separately in `scripts/ordinary_vscode_sidecar/`. Frozen product source, compiled output, dependencies, and existing editor acceptance helpers are read only. `--prepare` writes an exclusive metadata plan binding the helper/sidecar bytes, current product source and compiled files, actual prepared host, local Node executable, existing vsce 4.0.0 code, and source fixture. It does not package, install, or launch VS Code. The root agent must commit and independently review the stable sources before preparing the final plan. An explicit `--run` additionally requires that plan's literal file SHA-256 and an unused absolute output directory. Actual execution is separately authorized by the root after the fresh context benchmark and other native owners finish. The fixed session deadline is 2026-10-14 13:37:05 UTC; execution refuses an insufficient remaining cleanup budget.

An actual run uses vsce's existing `pack` function directly, without `packageCommand` or `vscode:prepublish`, to freshly package version 0.1.0's existing compiled payload. It records both VSIX archives, every archive member hash, and explicitly compares every packaged `dist/src` file to its prepared source byte hash. It also packages the local sidecar, version 0.0.1, and binds its executable source and manifest. Only these two local VSIX filenames are passed to the normal Code CLI. There is no marketplace extension ID, development-path flag, test-path flag, proposed-API enablement, or disable-extensions bypass. Each phase receives a separate unused extensions directory and user-data directory beneath a private owned root; no existing user settings, profiles, trust store, workspace, or extension installation is used.

Both profiles retain `security.workspace.trust.enabled=true` in their fresh settings. The **trusted** phase explicitly supplies `--disable-workspace-trust` and must observe `workspace.isTrusted=true`. This narrower trusted-local scope does not prove the interactive trust prompt or persisted trusted-folder UX. The **restricted** phase supplies no trust-disable flag and must observe `workspace.isTrusted=false` before every product command. The sidecar advertises ordinary untrusted-workspace support so it can observe the product's unsupported capability without overriding that product's enablement. It does not force `target.activate()` or use the target's exported test API. All connect/find/status attempts must be unavailable or deny execution, and the separate fixture must receive exactly zero product HTTP requests. An unavailable target is recorded honestly rather than treated as a successful activation.

The ordinary sidecar activates through `onStartupFinished` and must observe its supported extension context mode as `Production`. Product activation before/after connect is recorded; an already active view-triggered product is not mislabeled as command-caused activation. In the trusted profile it invokes supported public commands with structured arguments: `semanticSearch.connect`, default `semanticSearch.find`, `semanticSearch.preview`, `semanticSearch.open`, `semanticSearch.status`, and a second explicit Qwen-provider `find`. The first search must preserve shipped defaults (dense, no reranking, 4 candidates, 8 results, 12,000 source characters, 4,096 tokens, dependencies included; the old non-Qwen wire shape omits provider). The installed manifest records the default provider as H2O. The commands must reach the exact installed active product path and expose one literal tracked two-line source result. Captured preview and file navigation must show that source; file navigation must select lines 1–2 in a clean editor. The second search requests Qwen reranking, receives the fixture's structured `Qwen reranking is not configured` error, and must show the product's actionable `--enable-qwen-reranker` guidance. This establishes provider selection/error handling only; it supplies no synthetic reranking scores or inference success claim.

The HTTP service is an authored numeric-loopback schema fixture with bounded bodies and the real response/error shapes derived from the unchanged installed product parser and old acceptance helper. It rejects foreign Host/Origin headers, records every received attempt including denials, and has no embedding/model/index/cancel endpoint. The returned cl100k count of 128 is explicitly a **schema placeholder**, not independently measured token usage. Both model/inference counters are zero because the harness runs only JavaScript fixture logic, the unchanged HTTP editor client, and Git source eligibility/navigation checks. This experiment establishes installation, ordinary activation/enablement, command wiring, defaults, source validation, navigation, and cleanup; it makes no retrieval accuracy, real backend, inference speed, or coding-token claim.

Every child is spawned detached only after validating the canonical private owner root and nonce. Its PID/PGID/nonce is registered synchronously before any await, and its actual PGID is independently checked using `ps`. Before its first await the sidecar validates that nonce and proves its Code ancestry or owned group. Signal handlers are installed before any package/install/editor child; interruption stops future phases and signals only registered owned groups. Each command has a time/output cap. Normal completion, timeout, SIGINT, SIGTERM, and failure all retain actual command output, counters, and cleanup receipts. Cleanup uses TERM then bounded KILL escalation; absent groups plus no forced kill/errors are required for a clean acceptance. Failed or forced cleanup cannot certify success. Both installed payloads are rehashed afterward, original fixture source must remain unchanged, and owned fixture listeners must close. The private root is removed only after every owned group is proved absent, with its exact nonce checked again. Otherwise the root is retained and the receipt is unsuccessful. Public output contains the immutable VSIX archives, copied sidecar results, and an exclusive terminal receipt; root supervision may separately retain terminal output.

CPU tests use fake VS Code APIs, real tiny Node subprocesses, temporary inventories, and an authored loopback service. They do not invoke Code, vsce packaging, product/model servers, or any model. Preparation and tests are distinct from the later actual installed-profile acceptance proof.

Example preparation, after source review:

```sh
node scripts/ordinary_vscode_profile.cjs --prepare --output /ABS/NEW/ordinary-plan.json
```

Example actual invocation, only when root authorizes the serialized run:

```sh
node scripts/ordinary_vscode_profile.cjs --run --plan /ABS/ordinary-plan.json --expected-plan-sha256 LITERAL_SHA256 --output /ABS/NEW/ordinary-profile-results
```
