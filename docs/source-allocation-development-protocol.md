# Prospective source-aware allocation development replay

This CPU development experiment tests whether conservative source relationships
can select complementary definitions while a guard checks actual protected source
after packing. It follows the failed [literal-term allocation experiment](complementary-allocation.md).
No production default, release, retrieval, model, reranker order, source window,
score or context limit changes. TanStack Query remains reserved and unobserved
until a new candidate independently qualifies and a separate native plan is fixed.

## Immutable observed inputs and historical negative evidence

The same **365 observed first-repetition cases share 187 dataset/query units**:
90 Express/Zod language rows; 30 Express, 30 Zod and 28 Jinja native rows;
144 Qwen development and 15 HTTPX rows using their already scored
`hybrid_k24_b1` order; and 28 urllib3 native legacy rows. Former holdouts are
observed development evidence. Retrieval modes and reused queries are shared
observations, not independent trials. The candidate receives original ranked
snippets, scores, query text, source graph and canonical identities, never query
IDs, kinds, gold IDs, evidence intervals or benchmark outcomes.

The new profile reuses the existing CPU input loader, original physical-source
packer, exact compact tokenizer, offline import guard and original control
barriers. It references both immutable controls in
`results/window-development-2026-10-21/replay.jsonl.gz`. It also retains the
failed `aspect_fill` and `aspect_balanced` results in
`results/allocation-development-2026-10-26/replay.jsonl.gz` as historical negative
evidence. Those arms are read as original records and **never rerun**. No old
script, plan, trace, summary or audit is modified. Neither large ledger nor the
complete source inventory is copied into this study.

`control-references.json` and `negative-references.json` identify every referenced
record by one-based line number, canonical record SHA-256, full-response SHA-256
and exact compact-payload SHA-256. The record hash uses sorted-key, compact UTF-8
JSON without a newline. Both manifests require the exact 365-case membership.
Reports retain all six conditions, but qualification concerns only the two new
arms; historical failures cannot be recast as prospective results.

The original input anchor remains `5d1e80062638e19101acf3b9e8543066590fd1c5`.
The October 21 window study retains its actual original freeze, execution and
auditor commits despite the later rewritten history. Its committed blobs are
verified as immutable data; no historical producer is executed or attributed to
replacement code. The immediately preceding allocation study retains its actual
freeze `8c5f3f1` and execution `443b890`, with normal current-branch ancestry.
Both provenance receipts bind original source, inputs, frozen files, artifact
hashes and independent audits. A historical rewrite does not relax the new
study's strict prospective ancestry requirements.

## Conditions fixed before any new outcome

Every arm uses **8 excerpts, 12,000 source characters and 4,096 exact compact
JSON `cl100k_base` tokens**, original whole physical-line prefixes, static
dependencies enabled, extraction 160/40, and the original scored order. The Qwen
K24 order receives no unscored tail.

1. `legacy`: original display-label selection and unchanged postprocessing.
2. `coverage_control`: canonical-definition selection followed by the existing
   source-preserving covered-row removal and bounded ranked backfill. Its known
   gains do not count as new gains.
3. `aspect_fill`: immutable historical failed allocation record, referenced only.
4. `aspect_balanced`: immutable historical failed allocation record, referenced only.
5. `source_graph`: the source-neighbor proposal below, followed by protection of
   structurally selected **actual delivered** reference source after packing.
6. `source_graph_all`: the identical proposal, followed by protection of **every**
   actual delivered reference row after packing. This stricter control measures
   the consequence of protecting all old source rather than structural evidence.

The new proposal activates only for the existing two-to-four literal clause
detector. It starts with the unchanged canonical-definition selection, original
eligible list and dependency origins. Protect the first five ranked canonical
anchors, every original dependency and its owner. Use only one-hop caller/callee
edges incident to those anchors from the existing conservative `ReferenceGraph`.
Both endpoint display labels must resolve to exactly one canonical definition;
ambiguous, absent or malformed identities supply no edge. Protect any original
eligible definition that is an admitted neighbor.

Among original selected definitions absent from the original eligible list,
choose admitted graph neighbors in original raw rank order. Add at most two and
no more than the count of exchangeable original eligible slots. Evict the last
unprotected original eligible rows. The proposed order is protected original
rows in their original order, additions in raw rank order, then retained
unprotected original rows in their original order. The original selected list
and origins map remain unchanged. Added retrieved rows use the same standard
retrieval-origin fallback as other original scored rows. Original scores are
preserved; a graph witness supplies no model score or correctness claim.

Inactive clause detection, no valid graph witness, no exchangeable slot or no
new ranked graph neighbor returns the original definition selection. These
fallbacks and the two new modes are fixed before evaluation; there is no query
rewrite, diversity bonus, synonym expansion, term-rarity score, source union,
new retrieval or new model call.

## Actual postpacking source protection

Pack the proposal using the original character and exact compact-token packers,
then run the same source-preserving coverage postprocessor. Lazily construct
the unchanged `coverage_control` from the **same** raw pairs, graph, query and
limits. Development may supply the exact coverage response already reproduced
by its preceding 730-row control barrier; any later native implementation must
perform and time its real additional reference packing without another query
embedding or retrieval call.

For an accepted `source_graph` plan, protect reference rows whose IDs were
structurally protected by the plan, any delivered dependency, and any delivered
row whose canonical key is an admitted neighbor (including backfilled rows).
Also protect an entire actual reference row when its same-path physical interval
overlaps a structurally protected original window or an original graph-neighbor
window. The plan retains those literal original window descriptors in
`protected_windows`; this preserves anchors contained by another delivered row
after coverage coalescing. It uses original window ranges, not a broader
canonical definition range.

For `source_graph_all`, or any inactive/rejected plan, protect every actual
reference row. The guard sees these actual delivered physical source prefixes,
not an unreturned full window or lexical term inventory.

Each protected row must be covered by one actual proposal row with the same
path, complete physical interval, exact literal bytes, source provenance and
origin. A dependency also requires the same original identity and owner.
The dependency owner must actually remain in the proposal. Every row preserves
`related_to` key presence/value; an unchanged ID preserves the original full
content hash. Source-overlay metadata likewise preserves key presence/value.
Metadata must have valid physical bounds and SHA-256 source hashes. If the plan
is inactive or any protected source is absent or clipped, return the **exact**
reference response. Otherwise return the exact proposal response. The guard does
not retroactively repair a preexisting reference whose dependency owner was
already coalesced or clipped: such a proposal can be rejected while fallback
still returns the exact historical control. The guard does not receive gold or
claim that structurally protected rows are all relevant
implementations. Unprotected evidence losses still fail the independent quality
gate, including losses from already incomplete queries.

The actual pure planner runs once. Its defensive plan is carried through the
eligible list to the postprocessor. The actual pure guard runs once with that
plan, one reference and one proposal. Receipts and guard operands remain outside
the public response and compact client schema; the harness captures what ran,
not a later replacement plan. Original full source/cache identities remain
verifiable. Production selector and postprocessor aliases remain unchanged.

## Source graph trust boundary

Freeze `graph-fixtures.json` before new outcomes. It contains the complete graph
inventory for every original source fixture: sorted caller identities, original
target order, complete source-file hashes and hashes of `source.py`,
`languages.py`, `javascript.py`, `relations.py` and `javascript_relations.py`.
It is source-only data, not a candidate activation or gold-coverage result.

The independent auditor may use the unchanged `ReferenceGraph` strictly as the
conservative graph extractor, together with those source/parser modules and
pinned grammar libraries. It reconstructs graph inventory from independently
verified physical source and compares the frozen full graph. It independently
implements every source-aware plan and guard decision and may not import the new
planner, selector, producer, backend, index, model or numerical runtime. This is
an explicit shared extractor trust boundary, not a claim of an independently
implemented call-graph parser. Every admitted witness must be a literal frozen
edge whose canonical endpoints are unique.

## Prospective freeze, execution and auditing

Freeze recomputes only the **365 exact legacy controls** and **337 previously
observed coverage controls**. It binds all producer, selector, backend, source,
client-contract, independent-auditor and test bytes; this protocol; CPU/runtime
pins; original input/artifact hashes; source/definition/graph inventories; both
control manifests; immutable negative references; and both historical provenance
receipts. No new candidate is constructed or scored during freeze.

Commit all unchanged prospective source, tests, protocol, plan, gates, pointers
and graph/negative manifests before `--run`. Execution refuses changed or
uncommitted bound bytes, a non-ancestor freeze or existing attempt artifacts.
It claims an exclusive `run-start.json`, repeats the original 365/337 barriers,
and reproduces **all 730 full original control responses and compact payloads**
before either new candidate. The control gate records zero preceding new
outcomes. The two historical negative arms are verified and referenced rather
than evaluated again.

The new ledger stores only **730 new candidate traces**: original raw, selected
and eligible source/score stages; canonical keys and origins; actual planner
receipt and guard-plan operand; prepostprocessor, proposal, reference and final
responses; actual guard receipt/call counts; backfill and ranked source rows;
exact compact text/hash/tokens; both control references; and every reporting
gain/loss. All producer calls use the offline import/network guard. No model,
index, retrieval, reranking, GPU, numerical runtime or network work is allowed.

Retain failures, partial progress and exclusive attempt files. Never resume or
overwrite an attempted run. A repair requires a new output directory, reviewed
source bindings and a new committed freeze. Commit the canonical independent
auditor and its adversarial tests before running it; retain failed audit attempts
under distinct output names.

After the complete control gate, open the new gzip ledger exclusively and write
and flush each completed candidate trace before starting the next. An exception
closes the gzip stream, preserving a readable partial ledger alongside the
failure receipt's attempted/completed counters. Summary and findings are emitted
only after the full declared candidate matrix completes.

## Qualification and scope

Report all metrics and every individual group/complete-query change by original
study, dataset and retrieval/reranker condition. A new arm qualifies only with
**zero full-group losses, complete-positive losses and single-file first-hit
losses against both controls**, and at least **one additional distinct complete
dataset/query unit beyond `coverage_control`**. Partial-query group losses count;
known previous gains cannot qualify. Scoped absent queries remain in reports but
returned or omitted candidates do not prove feature absence.

Historical development retains its original path plus full physical-evidence
interval scoring. Do not pool it with the stricter qualified-symbol/hash scoring
reserved for fresh TanStack validation. If both candidates qualify, prefer more
additional distinct complete multi-file queries, then more additional distinct
complete queries overall, then fewer changed cases; the final tie prefers
`source_graph_all`. Fix one choice before any fresh outcome. If neither qualifies,
record the negative result and leave TanStack unobserved.

Only an independently audited qualifier may enter a separately frozen native
experiment with both controls and native warm timing. No automatic default
change, release or coding comparison follows this replay. Source-evidence
coverage does not establish coding correctness, billed token savings, faster
completion, generalization or value to external users.
